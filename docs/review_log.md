### 2. 工作模式设计讨论

用户认为当前单一自主执行模式"过于简单，没达到准研究生水平"，提议增加 PLAN 和 FEEDBACK 模式。经讨论，确认以下 4 种工作模式：

#### 2.1 模式清单（用户确认全部包含）

| 模式 | 名称 | 核心特征 |
|------|------|----------|
| PLAN | 规划模式 | 先生成结构化计划，用户审批后执行 |
| WORK | 工作模式 | 自主执行，危险操作需确认（当前模式增强） |
| FEEDBACK | 反馈模式 | 关键决策点暂停，等待用户反馈 |
| RESEARCH | 研究模式 | 只读调查，不可修改文件 |

#### 2.2 PLAN 模式 — 用户确认的设计决策

**问题**：用户审批计划后是否可以编辑计划步骤？

**用户选择**：完全自由编辑
- 用户可以批准部分步骤、拒绝部分步骤
- 用户可以新增步骤
- 用户可以调换步骤顺序
- 用户可以修改步骤内容

**实现影响**：
- 前端需要完整的计划编辑器（增删改排序步骤）
- WebSocket 需要传输编辑后的计划结构
- Agent 接收修改后的计划作为执行依据
- 预计增加 2-3 小时前端开发时间

#### 2.3 FEEDBACK 模式 — 用户确认的设计决策

**问题**：Agent 在什么粒度暂停等待反馈？

**用户选择**：关键决策点暂停
- Agent 自主执行，仅在重要节点暂停
- 暂停点：写文件前、执行命令前、删除文件前、计划变更时
- 类似 WORK 模式 + 增强确认机制
- 暂停时用户可选：继续 / 调整（附带反馈文字）/ 停止

**实现影响**：
- 需要定义"关键决策点"的判定逻辑
- 复用后端 `classify_risk()` 判定是否为关键决策
- WebSocket 推送 `feedback_request` 事件
- 前端显示反馈选项（继续/调整/停止）

#### 2.4 模式切换 — 用户确认的设计决策

**问题**：用户是否可以在任务执行过程中切换模式？

**用户选择**：PLAN 批准后自动转 WORK
- 创建任务时选择模式
- PLAN 模式：计划批准后自动转为 WORK 模式执行
- 其他模式：执行过程中不可切换
- 实现简单，语义清晰

### 3. 技术影响分析

#### 3.1 后端 API 适配层影响

- `AgentSession` 需要支持 `mode` 参数（PLAN/WORK/FEEDBACK/RESEARCH）
- PLAN 模式：Agent 调用 `create_plan` 工具后暂停，等待 WebSocket 推送审批结果
- FEEDBACK 模式：关键决策点（write_file/delete_file/run_command 前）暂停
- RESEARCH 模式：过滤可用工具列表，移除写操作工具
- WebSocket 新增事件类型：
  - `plan_created`：Agent 生成计划
  - `plan_approved`：用户审批计划（含编辑后的步骤）
  - `feedback_request`：关键决策点暂停
  - `feedback_response`：用户反馈

#### 3.2 前端影响

- 侧边栏需要工作模式选择器
- PLAN 模式需要计划编辑器组件
- FEEDBACK 模式需要反馈选项 UI
- RESEARCH 模式需要只读标识
- 模型选择器组件（内置 + 自定义）
- 文件上传组件
- 任务列表（分组/列表视图切换、搜索）

### B. 核心创新点

**1. 三层架构设计**

```
Execution State（当前轮） — 不可压缩
    ↓
Context（历史消息） — 可压缩
    ↓
Workspace（文件系统） — Source of Truth
```

**2. 事件驱动 + 阈值驱动混合压缩**
- 写后失效：write_file 成功立即失效旧读取（事件驱动）
- 按需重读：大型结果压缩为元信息（阈值驱动）
- 工作集保留：最近 5 轮完整保留

**3. 零误报安全机制**
- 精确率 100%：不会误拦正常操作
- 命令分级 100% 准确：23 个危险命令全拦截，25 个安全命令全放行
- 代码扫描保守策略：宁可漏报不误报

### C. 常见问题应答

**Q: 为什么不用 LangChain？**

预推免要求从零实现展示系统设计能力。自主实现让我深入理解：
- Agent 循环的状态管理
- 上下文窗口的优化策略
- 安全边界的设计权衡

这些是用框架学不到的。

**Q: 35.4% 压缩率够吗？**

- 文件密集场景达 65.2%
- 命令场景 0% 是合理的（结果本身简短）
- 平均 35.4% 可将 128K 窗口扩展到约 200K 有效容量
- 压缩耗时仅 0.26ms，性能开销可忽略

**Q: 代码扫描召回率 55.6% 是否太低？**

这是**工程权衡**：
- 精确率 100%：零误报，不影响开发体验
- 高危代码（eval, exec, os.system）检测率 100%
- 边缘 API 漏报可通过扩展规则改进
- 设计哲学：宁可漏报，不可误报

**Q: 与 Claude Code / Codex 的差距？**

- 差距：工具丰富度、模型优化、UI 体验
- 优势：核心能力已实现并量化验证
  - 上下文管理：35.4% 压缩率
  - 安全机制：85.7% 准确率，100% 精确率
- 定位：研究原型，证明技术可行性

**Q: 最大的技术挑战是什么？**

**上下文一致性**问题：
- 挑战：压缩历史消息后，如何保证当前工具执行不受影响？
- 解决：Execution State 独立提取，压缩只修改历史，不触碰当前轮
- 验证：31 个测试全通过，无一例因压缩导致错误
